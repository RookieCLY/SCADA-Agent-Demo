### 1.3 Runner 与实验产物规范

`eval.runner` 把一次实验 run 固定为如下目录结构:

```text
results/{config_name}/{model}/{run_id}/
├── traces.jsonl       # 每条 golden × rep 一条完整 trace
├── _meta.json         # config hash / git commit / dirty 状态 / dataset split / counts / judge_model
├── _config.yaml       # config 快照
├── _failures.jsonl    # 技术失败与重试耗尽记录
└── judges.jsonl       # 离线 Judge 输出占位或结果
```

关键实现点:

- `--golden-ids golden-001,golden-002`:指定 case
- `--all`:全量 100 条
- `--reps N`:每条重复 N 次
- `--resume`:按 `(golden_id, rep_index)` 跳过已完成 trace
- `--max-reruns`:重试技术失败
- `--freeze`:实验结束后可把产物文件设为只读,防止误改
- `_meta.json` 中记录 `config_hash`、`code_commit`、`git_dirty`、`dataset_version`、`dataset_split`、`selected_golden_ids` 等复现实验所需字段

### 1.4 Deterministic Metrics 指标体系

`eval/metrics.py` 实现了确定性评分层。当前核心指标包括:

| 类别 | 指标 | 说明 |
| --- | --- | --- |
| Tool 选择 | `tool_selection_precision` / `recall` / `f1` | 在统一逻辑 Tool 空间评分,扁平 `create_xxx` 与分层 `manage_domain(action=xxx)` 映射到同一 `(domain, action)` |
| Tool 选择 | `hallucinated_tool_rate` | 不存在的 Tool 或非法 action 比例 |
| Tool 选择 | `out_of_scope_tool_rate` | 当前状态/Workflow 白名单外调用比例 |
| 领域/action | `domain_match_accuracy` / `action_match_accuracy` | 分层诊断 domain 选错还是 action 选错 |
| 终态 | `final_state_match` / `final_state_report` | 基于 world diff 与 `expected_final_state_diff` 比对 |
| 终态 | `match_mode` | 支持 `strict` / `subset` / `key_fields` |
| 参数 | `parameter_validity` / `parameter_match` / `schema_violation_rate` | 区分 schema 是否有效与关键字段是否命中 |
| 轨迹 | `trajectory_match` / `terminal_state_match` / `step_efficiency` / `order_correctness` | 检查 required/forbidden tools/actions、终态、步数边界、编辑距离 |
| 错误码 | `expected_error_code_match` / `error_code_distribution` | 负例或 fail_or_clarify 的错误码验收 |
| 稳定性诊断 | `loop_stuck` | early termination 或 UNKNOWN 终态 |
| 级联失败 | `cascade_failure_count` / `cascade_failure_rate` | 后续引用了前置失败的 intended entity 时计数 |
| Resource 协同 | `resource_query_before_action` | 写 world 前是否先读 Resource |
| 成本/性能 | `input_tokens` / `output_tokens` / `cost_usd` / `e2e_latency_ms` | 从 trace totals / llm_calls 聚合 |

评分维度:

- `task_completion`
- `tool_correctness`
- `parameter_correctness`
- `step_efficiency`
- `clarification_or_rejection_quality`
- `communication_quality`
- `overall`

## 3. 关键 Bug 诊断与修复记录


### 3.1 非终态停在 MANAGE_PAGES 而不是 DONE

**现象**:

真实 LLM 有时完成业务操作后输出普通文本“主监控页面已成功创建”,但 run terminal state 仍是 `MANAGE_PAGES`,没有进入 `DONE`。

**原因**:

orchestrator 只有在收到有效 `resp.next_state == "DONE"` 或 workflow/state transition 明确推进时才会把状态置为 DONE。真实 OpenAI-compatible LLM path 当前并不会从普通文本中解析 `next_state: DONE`;如果模型没有 tool call、也没有 machine-readable next_state,主循环会以当前 operational state 结束。

fix:

系统提示中已经加入:

```text
完成任务后明确告知用户，并在回复的纯文本中包含 "next_state: DONE" 来结束整个任务
```
